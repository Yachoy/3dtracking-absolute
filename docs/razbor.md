> Разработать систему автоматического **определения** и **сопровождения** заданного объекта на видео

## 2. Что лежит в данных (`project2.7z`)

Сцена отрендерена в **Unreal Engine** (горы, деревья, снег). Объект — **грузовик-фура**.

| Файл | Что это |
|---|---|
| `Way1.FinalImage.CineCameraActor{1..5}.mp4` | 5 видео с 5 разных камер, 1920×1080, 30 fps, 1001 кадр (~33 с) |
| `object_transform_CineCameraActor{N}.csv` | положение и поворот камеры **на каждом кадре** + фокусное расстояние |
| `object_transform_SM_AA_track.csv` | **истинная траектория грузовика** (ответ!) — Frame; X; Y; Z |

Детали:
- Единицы — **сантиметры** (стандарт Unreal). Ось Z — вверх.
- Поворот: Roll / Pitch / Yaw в градусах (конвенция Unreal).
- Фокусное: камеры 1–5 = 35 / 60 / 35 / 50 / 20 мм. Матрица (сенсор) 23.76 × 13.365 мм.
  Отсюда фокус в пикселях: `fx = focal_mm / 23.76 * 1920`.
- Камеры 1–4 стоят неподвижно. **Камера 5 поворачивается** (yaw меняется с −164° до 104°) — но её поза всё равно дана на каждом кадре.
- Грузовик едет ~400 м за 33 с (~45 км/ч), Z ≈ 3.0–3.6 м (рельеф).
- Сложности: грузовик **перекрывается деревьями и холмами**, уходит из кадра, далеко (до 500 м) — маленький.

### Проверено: математика сходится

Скрипт [`tools/check_projection.py`](../tools/check_projection.py) берёт истинную 3D-точку грузовика
и позу камеры, проецирует в кадр и рисует кружок — **кружок попадает на грузовик**.
Значит, формулы камеры мы поняли правильно. Важная деталь: точка траектории — это
**перед кабины у земли** (pivot модели), а не центр кузова. Это надо учитывать при ответе!

## 3. Главный вывод: задача проще, чем думал сокомандник

Сокомандник рассуждал про худший случай — **одна** камера, которая сама двигается и её поза неизвестна
(тогда нужен SLAM, DUSt3R/VGGT, оценка глубины и т.п.).

У нас же **5 камер с точно известными позами**. Это классическая **многокамерная триангуляция**:

```
 Камера 1 ──луч──┐
 Камера 3 ──луч──┼──►  точка, где лучи «почти пересекаются» = 3D-позиция грузовика
 Камера 4 ──луч──┘
```

Луч из камеры через пиксель с грузовиком — это прямая в 3D. Две и более прямых → точка.
Математика: DLT / метод наименьших квадратов (`cv2.triangulatePoints` или 20 строк numpy).

Ещё бонус: даже если грузовик виден только в **одной** камере — можно пересечь луч с **землёй**
(Z ≈ 300–360 см, или по известному рельефу из предыдущих кадров).

SLAM / VGGT / DUSt3R / Depth Anything — **скорее всего не нужны** (запасной вариант, если в проверочном
наборе позы камер не дадут или они будут с шумом — на это стоит посмотреть 4-го в 20:00).

## 4. Как это должно работать (пайплайн)

```
 5 видео ──► [1. Детектор] ──► рамки грузовика на каждом кадре каждой камеры
                  │
                  ▼
           [2. Трекер 2D] ──► сглаживает рамки, держит объект при перекрытиях,
                  │            отсеивает ложные срабатывания
                  ▼
           [3. Точка в кадре] ──► из рамки берём пиксель «перед кабины у земли»
                  │
                  ▼
           [4. Триангуляция] ──► лучи из всех камер, где виден грузовик → 3D-точка
                  │              (RANSAC: выкидываем камеры, где детектор ошибся)
                  ▼
           [5. Фильтр Калмана / сглаживание] ──► заполняем дыры, убираем дрожание
                  │   (можно смотреть «в будущее» — мы обрабатываем видео офлайн)
                  ▼
           CSV: Frame; X; Y; Z
```

Пояснения по каждому блоку простыми словами:

1. **Детектор** — нейросеть, которая на картинке рисует рамку вокруг объекта и пишет «truck, 0.87».
   Грузовик есть в стандартном датасете COCO (класс `truck`), так что готовые модели его уже умеют.
2. **Трекер** — связывает рамки между кадрами («это тот же грузовик, что секунду назад»).
   Помогает, когда детектор на кадре промахнулся или грузовик за деревом.
3. **Точка** — триангулировать надо одну и ту же физическую точку во всех камерах.
   Центр рамки ≠ перед кабины, поэтому надо будет поправлять (см. п.7).
4. **Триангуляция** — чистая геометрия, нейросеть не нужна.
5. **Фильтр Калмана** — «предсказать, где объект будет, и подправить по измерению». Грузовик едет
   плавно, поэтому фильтр сильно уменьшает ошибку.

> **Ограничение (решили в команде): обработка строго онлайн.** Для кадра t можно использовать только
> кадры t, t−1, t−2, … Никаких обратных проходов, RTS-сглаживания, fixed-lag, двунаправленного SAM.

## 4.1. Онлайн-схема и baseline

Идея: **трекер живёт в 3D**, а не в каждой камере отдельно. Тогда проблема «тот же ли это объект в
другой камере» решается сама — все камеры поставляют измерения одного 3D-трека.

Цикл на кадре t:

```
состояние с t−1:  x = [X, Y, Z, Vx, Vy, Vz],  ковариация P
   │
   ├─ 1. PREDICT   Калман: x⁻ = F·x,  P⁻ = F·P·Fᵀ + Q          (dt = 1/30 с)
   ├─ 2. PROJECT   x⁻ → пиксель + эллипс неопределённости в каждой из 5 камер (позы камер на кадре t)
   ├─ 3. DETECT    детектор на кадре t каждой камеры (полный кадр или ROI вокруг прогноза)
   ├─ 4. GATE      в каждой камере берём детекцию, ближайшую к прогнозу, если она внутри эллипса
   ├─ 5. MEASURE   ≥2 камер → триангуляция (DLT + RANSAC по ошибке перепроекции)
   │               1 камера → луч ∩ плоскость Z = Z⁻
   │               0 камер  → нет измерения
   ├─ 6. UPDATE    Калман: x = x⁻ + K·(z − H·x⁻)
   └─ 7. OUTPUT    (X, Y, Z) на кадре t  → пишем строку в CSV
```

Состояние трека: `TRACKING` → (нет измерений N кадров) → `LOST`: только predict, gate расширяется →
(≥2 камеры согласованно увидели объект) → `TRACKING`.

Инициализация: на первых кадрах детектим везде, перебираем пары детекций из разных камер,
триангулируем, оставляем гипотезу с минимальной ошибкой перепроекции во всех камерах.

- **По детекциям (MOT):** ByteTrack / BoT-SORT — встроены в ultralytics (`model.track(...)`). Самый простой вариант.

### SAM 2 / SAM 3 (Meta) — детектор и трекер в одной модели

- **SAM 2** (2024): даёшь на 1-м кадре точку/рамку объекта → модель ведёт **маску** объекта по всему видео,
  держит память, переживает перекрытия. Сама объект не находит — ей надо показать.
- **SAM 3** (ноябрь 2025) + **SAM 3.1** (март 2026): то же самое, но объект можно задать **текстом**
  («white truck»). Т.е. детекция + сегментация + трекинг сразу. Есть в HF Transformers
  (`Sam3VideoModel`) и в ultralytics.
- Зачем нам: маска точнее рамки (видно, где кабина, где колёса касаются земли) →
  точнее точка для триангуляции. И не нужно отдельно склеивать детектор с трекером.
- Минусы: тяжёлая, нужна видеокарта (5 камер × 1001 кадр на CPU — очень долго);
  может «перепрыгнуть» на похожий объект или потерять после долгого перекрытия.
- Как использовать: **как основной трекер** (текстовый промпт или рамка от YOLO на первом кадре),
  либо как «уточнялку» — YOLO даёт рамку, SAM даёт по ней маску.

### Если камеры окажутся без поз (план Б)

VGGT / DUSt3R / MASt3R — нейросети, восстанавливающие позы камер и 3D-сцену по картинкам.
LightGlue / RoMa — сопоставление точек между кадрами. Depth Anything V2 — глубина по одной картинке.

## 5.1. Как понять, что в разных камерах — один и тот же объект

Внешний вид между камерами почти бесполезен: в одной камере грузовик виден спереди с 65 м,
в другой — сбоку с 550 м (10 пикселей). Зато мы **знаем позы камер**, поэтому главный инструмент — **геометрия**:

1. **Пересечение с землёй.** Луч из камеры через низ объекта ∩ поверхность земли → точка (X, Y) на карте.
   Один и тот же объект из разных камер даёт **почти одну и ту же точку**. Разные объекты — далеко друг от друга.
2. **Эпиполярная линия.** Объект в камере A → в камере B он обязан лежать на конкретной линии.
   Кандидаты далеко от линии — точно не он.
3. **Ошибка перепроекции.** Триангулируем гипотезу «это один объект» → проецируем 3D-точку обратно во все
   камеры → если везде попадает в рамки (ошибка в пикселях маленькая), гипотеза верна. Перебор пар + RANSAC.
4. **Время.** Сравниваем не отдельные детекции, а **треки** (траектории за N кадров): один объект движется
   синхронно во всех камерах. Это намного надёжнее одного кадра. Сопоставление — венгерский алгоритм
   (`scipy.optimize.linear_sum_assignment`) по матрице «расстояний».
5. **Внешний вид — только как доп. признак**: цвет/класс, эмбеддинги DINOv2/v3, CLIP, ReID-модели.

Порядок: 2D-трек в каждой камере отдельно → геометрическая склейка треков между камерами →
триангуляция → Калман. А 3D-трек «заданного объекта» затем проецируется в камеры и помогает
снова найти его там, где он потерялся (повторный захват).

Проверить: есть ли в сцене **другие** машины/похожие объекты. Если грузовик один — сопоставление
почти тривиально, но решение всё равно стоит сделать общим (на проверочном наборе может быть иначе).

## 6. Датасеты

Главное: **размечать руками почти не нужно**. У нас есть истинная траектория →
проецируем грузовик в каждую камеру → получаем разметку автоматически
(рамка = проекция 3D-коробки грузовика, ~10 × 2.5 × 3.5 м, направленной по движению).
На этом можно **дообучить детектор** именно под нашу сцену.
Осторожно: если грузовик за деревом, проекция всё равно есть — такие кадры надо отфильтровать
(например, оставлять только те, где предобученный детектор тоже что-то видит рядом).

Внешние датасеты (если нужно больше данных / для презентации):
- **COCO** — на нём предобучены все детекторы, класс `truck` уже есть.
- **VisDrone**, **UAVDT** — транспорт, снятый издалека / сверху (маленькие объекты).
- **UAV123**, **LaSOT**, **GOT-10k** — бенчмарки трекинга (их называл спикер Пеленга).
- Синтетика: **CARLA**, **AirSim** — тоже рендер на Unreal, похоже на наши данные.

Ищутся на huggingface.co/datasets по названию.

## 7. Подводные камни

1. **Какая точка — ответ.** Траектория = перед кабины у земли. Детектор даёт рамку — нужна поправка
   (сдвиг от центра рамки к носу кабины по направлению движения).
2. **Перекрытия.** Если камера видит грузовик за деревом, рамка кривая → RANSAC + веса по уверенности.
3. **Разное время/синхронизация.** Проверить, что кадр N во всех видео — один и тот же момент
   (на cam2 проекция немного смещена — стоит разобраться).
4. **Первая строка CSV камер** содержит мусор в лишних колонках («Камера; 23,76*13,365мм») — читать только первые 7 колонок.
5. **Метрика.** Узнать у организаторов, как именно считают ошибку (MAE в метрах? по всем кадрам?).

## 9. Результаты baseline v0 (тестовый набор, 3 ноября)

YOLO26s (COCO, CPU, ~0.3 с/кадр) + онлайн EKF по пикселям + сдвиг до точки-ответа, подобранный по GT.

| Метрика | Значение |
|---|---|
| Покрытие кадров | 72% |
| MAE 3D | 13.9 м |
| Медиана 3D | 7.2 м |
| p90 3D | 34.4 м |
| MAE Z | 1.5 м |

Что выяснили:
- Детектор нормальный: камера 1 — 100% кадров, где грузовик в кадре; камера 5 — 52%; ложных рамок мало.
  Остальные «промахи» — грузовик закрыт горами.
- Когда грузовик видит только **одна** камера (кадры 800+, только камера 5), глубина вдоль луча плохо определена →
  трек уплывает до 20–60 м. Это главный источник ошибки.
- Центр рамки — разная 3D-точка в разных ракурсах (фура ~16 м): сбоку это середина прицепа, спереди — кабина.
- Пробовали и **отказались**: затухание скорости при потере (эффекта ноль), старт трека по одной камере
  (ухудшило до 33 м).
- В GT две битые ячейки (кадры 402 и 691) — читаются как пропуски.

Следующие шаги по ожидаемому эффекту:
1. Точка у земли вместо центра рамки (низ рамки / маска SAM) + ограничение «объект на земле» для одной камеры.
2. Модель фуры: 3D-коробка, ориентированная по скорости, — сравнивать с рамкой целиком, а не с центром.
3. Дообучить детектор на авторазметке из GT — поднять recall в камерах 2–4.

## 10. v1: точка у земли + высота рамки (3 ноября)

Измерение от каждой камеры теперь `(u, v_низ, h)`: середина нижнего края рамки (где колёса касаются земли)
и высота рамки в пикселях. Высота объекта одинакова с любого ракурса → `h ≈ fy·H / дальность` →
даже одна камера даёт 3D-точку, а не только луч. Высота H подбирается по GT (`run.py --calibrate`,
сохраняется в `config/tracker.json`).

| Вариант | Покрытие | MAE 3D | Медиана | p90 |
|---|---|---|---|---|
| v0: центр рамки | 72% | 13.9 м | 7.2 м | 34.4 м |
| низ рамки без высоты | 72% | 16.2 м | 11.5 м | 33.7 м |
| низ рамки + высота (`--no-single-init`) | 72% | 10.8 м | 9.0 м | 21.2 м |
| + старт трека по одной камере (**по умолчанию**) | **93%** | 12.4 м | 9.1 м | 26.1 м |

- Калибровка дала высоту грузовика **8.9 м** и сдвиг до точки GT ~12 м вперёд, ~3.9 м вверх —
  модель фуры в сцене, похоже, увеличена ~в 2 раза, а точка GT — на кабине, не у земли.
- Старт по одной камере добавляет 208 кадров (ошибка на них ~13.5 м), но на уже покрытых кадрах
  ошибка растёт 10.8 → 12.1 м. **Что выбрать, зависит от метрики** — уточнить у организаторов,
  штрафуют ли кадры без ответа.
- Худшие участки: кадры 0–300 (грузовик далеко/за деревьями, работает в основном одна камера).

## 11. v2: шум модели движения (3 ноября)

Корень ошибки на кадрах 170–330: ещё пока трек видит грузовик, направление скорости ошибалось на 25–40°,
и при потере объекта трек улетал не туда. Причина — шум модели движения `accel_xy = 3 м/с²` был слишком мал:
грузовик поворачивает резко (вплоть до 90°), фильтр «не верил» поворотам. Подобрали `accel_xy = 12 м/с²`.

| Вариант | Покрытие | MAE 3D | Медиана | p90 | Макс |
|---|---|---|---|---|---|
| v1, по умолчанию | 93% | 12.4 м | 9.1 м | 26.1 м | 53 м |
| **v2, по умолчанию** | **93%** | **9.8 м** | 7.6 м | 23.4 м | 34 м |
| v2, `--no-single-init` | 72% | 8.7 м | 7.1 м | 16.6 м | 31 м |

Пробовали и **отказались**:
- использовать рамки, обрезанные краем кадра (без центра / без центра и высоты) — помогает при выезде из кадра,
  но портит въезд: видна только кабина, она ниже прицепа → дальность завышена. В сумме хуже.
- перезапускать потерянный трек по новой детекции — эффекта ноль.
- держать трек без измерений 5–10 с вместо 3 — покрытие 100%, но MAE растёт до 15–17 м.
- уменьшать шум модели (0.25–1.5 м/с²) — сильно хуже.

⚠️ `accel_xy`, высота объекта и сдвиг подобраны на **том же** тестовом наборе, на котором меряем —
на проверочном наборе ошибка будет выше. Плато 8–16 м/с² широкое, так что 12 должно переноситься.

## 12. v3: заполнение пропусков YOLO оптическим потоком (3 ноября)

`tracker/flow_fill.py` — 2D-трекер по каждой камере в духе Median Flow:
сетка точек в рамке → пирамидальный Лукас–Канаде → проверка «вперёд-назад».
Движение камеры вычитается точно: центры камер неподвижны, камера 5 только поворачивается,
поэтому фон смещается по гомографии `K·R_to·R_fromᵀ·K⁻¹` из известных поз. Точки, которые
двигаются как фон (деревья, горы внутри рамки), отбрасываются — рамку ведут только точки объекта.
Если объект ехал, а движущихся точек не осталось — он перекрыт/ушёл, рамка обрывается
(иначе она «прилипает» к фону).

- **вперёд**: от последней рамки YOLO, пока YOLO молчит — онлайн;
- **назад**: когда YOLO снова нашла объект, идём назад по прошедшим кадрам до прошлой рамки.
  В режиме `--replay` трек откатывается к началу пропуска и пересчитывается до текущего кадра:
  выданные ответы не меняются (строгий онлайн), но текущее состояние (позиция/скорость) точнее.
  Пересчитанные ответы для прошлых кадров пишутся отдельно в `*_delayed.csv` — это уже с задержкой.
- рамкам потока доверяем меньше, чем YOLO: шум ×(1 + 0.1·возраст в кадрах).

| Режим | Покрытие | MAE 3D | Медиана | p90 |
|---|---|---|---|---|
| YOLO (v2) | 93% | 9.8 м | 7.6 м | 23.4 м |
| + поток вперёд (`--flow`) | 99.5% | 9.5 м | 7.6 м | 22.3 м |
| + пересчёт по обратному проходу (`--flow --replay`), **строгий онлайн** | 99.5% | **9.0 м** | 7.3 м | 18.3 м |
| то же, ответы с задержкой (`trajectory_delayed.csv`) | 99.5% | 8.4 м | 6.4 м | 16.1 м |

- Кадров с ≥3 камерами стало в разы больше: было 18, стало ~280 (онлайн) / ~430 (с задержкой).
- Участок 200–300 (перекрытие): 23 → 12.5 м онлайн, 10 м с задержкой.
- Хрупкость: при малом росте шума с возрастом (0.02) и длинных рамках (90 кадров) — 20 м. Шум 0.1 устойчив.
- Не решено: в конце видео грузовик тормозит до остановки, трек продолжает ехать ~22 м/с (ошибка до 22 м).
- В камере 2 на кадре 240 грузовик хорошо виден, но ни YOLO, ни поток его не держат — нужен лучший детектор.

## 13. v4: 3D-модель фуры из FBX (3 ноября)

`tracker/truck_model.py` читает бинарный FBX (свой маленький парсер, без Blender/FBX SDK),
собирает все детали в одну выпуклую оболочку (101 точка) и подгоняет по 765 рамкам YOLO:

| Что | Значение |
|---|---|
| модель в файле | 6.68 × 1.68 × 2.42 м, начало — на земле посередине |
| **масштаб в сцене** | **×3.12** → фура 20.8 × 5.2 × 7.5 м |
| **точка GT** | **перед кабины**: 3.40 м вперёд от центра модели (передний край — 3.36), 0.97 м вверх (в сцене 10.6 и 3.0 м) |
| совпадение проекции модели с рамкой YOLO | медианный IoU 0.82 |

Трекер с моделью: трек — центр фуры на земле, направление — по скорости. Модель ставится в позицию
трека, проецируется, и с рамкой YOLO сравниваются все 4 края; края, упёршиеся в границу кадра,
выкидываются (обрезанные рамки снова полезны). Точка-ответ — перед кабины по модели.

Два важных урока:
- **рамка не должна влиять на скорость.** Если якобиан брать и по скорости (направление ← скорость),
  фильтр «доворачивает» фуру под ошибки рамки, направление уплывает с 90° до −16°, ошибка 40 м.
  Якобиан только по позиции.
- **модель — только когда направление известно** (скорость > 2 м/с и ≥10 обновлений). До этого —
  измерение по низу и высоте рамки, ответ — центр фуры (не угадываем, где кабина).

| Режим | Покрытие | MAE 3D | Медиана | p90 |
|---|---|---|---|---|
| без модели, YOLO | 93% | 9.9 м | 7.6 м | 23.4 м |
| **с моделью, YOLO** | 95% | 8.3 м | 4.7 м | 22.7 м |
| без модели, поток + пересчёт (строгий онлайн) | 99.5% | 9.1 м | 7.3 м | 18.8 м |
| **с моделью, поток + пересчёт (строгий онлайн)** | 99.5% | **7.2 м** | **4.8 м** | **15.8 м** |
| с моделью, с задержкой | 99.5% | 6.9 м | 4.4 м | 15.9 м |

- Пороги включения модели (1–4 м/с, 0–30 обновлений) почти не влияют: 7.2–7.8 м.
- Участки, где трек идёт по модели, — 1–3 м. Остаток ошибки — старт (кадры 0–100: грузовик трогается,
  одна камера, скорость переоценивается) и слепой участок 200–300.
- Модель считает фуру жёсткой; на поворотах прицеп изгибается относительно кабины — небольшое расхождение.
- Масштаб и точка-ответ подогнаны по GT тестового набора. Если в проверочном наборе та же фура —
  переносится как есть.
