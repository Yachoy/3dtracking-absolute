# Ответ на каждом кадре: без провалов (Way2) — проверьте на своём железе

Ветка `way2-no-gaps` от `codex/online-tracking` (`0342289`, трекер `--global-seg`).

## Проблема

`ConsensusTracker` после секунды без засечки двумя камерами объявляет `lost` и не выдаёт координат.
На демо Way2 это 396 кадров из 1933 (20 %), четыре провала на графиках:

| Кадры | Что там |
|---|---|
| 0–46 | старт, фуру видит одна камера — для захвата нужны две |
| 815–1041 | пыль: фура видна целиком в камере 4, но YOLO даёт ей 0,05–0,14 (порог 0,16–0,30) |
| 1418–1499 | фуру не находит ни одна YOLO |
| 1907–1932 | конец записи |

Пустой кадр — худший ответ: любая разумная оценка ближе к фуре, чем ничего.

## Что сделано

`online/estimation/gap_fill.py` — `GapFill`, включён по умолчанию с `--global-seg`
(выключить: `--no-fill-gaps`). Работает **только с выходом**: состояние трекера не меняется,
поэтому все кадры, где трекер выдаёт позу, остаются **бит в бит прежними** (v1 проверена на первых
51 кадре Way2: 9 кадров трекера совпали, 42 пустых заполнены). На кадре без позы:

1. **`predicted`** — прогноз от последнего ответа. Скорость — наклон траектории за последнюю
   секунду надёжных кадров трекера (`multi`/`mono`/`mask_multi`), а не его сглаженная скорость,
   которая в прогнозе затухает (из-за неё в v1 прогноз почти стоял, пока фура ехала в камере 4).
   Затухание 0,2 % за кадр, высота — уровень дороги по многокамерным засечкам.
2. **`weak`** — поправка по наблюдениям: 2D-маски SAM2 (`tracked_2d`, камера 4 после пропуска YOLO),
   маски, которые трекер нашёл, но отбросил, и YOLO с порогом 0,05 около проекции прогноза — случай
   с дымом. Две камеры с согласованными лучами — триангуляция. Одна камера — направление надёжно,
   дальность по размеру маски нет (в v1 отсюда рывки до 50 м за кадр), поэтому берётся точка луча
   на высоте дороги или ближайшая к прогнозу: правится только поперечная к лучу составляющая.
   Нужно совпадение силуэта CAD с маской (IoU ≥ 0,35).
3. **Плавность** — ответ тянется к измерению частично (35 % за кадр для одной камеры, 60 % для
   двух) и не сдвигается за кадр дальше `max(1,5 м, 2 × предельная скорость / fps)` — тот же
   допуск, что у трекера.
4. **`guess`** — до первого захвата (кадры 0–46): сначала триангуляция двух свежих детекций с
   согласованными лучами (в v1 была одна камера — отсюда 46 м на кадре 47), иначе одна уверенная
   детекция.

**Стык с трекером.** Кадр, где трекер вернулся, выдаётся как есть (условие «не трогать кадры
трекера»), поэтому скачок на стыке равен ошибке заполнения на последнем кадре провала. v2 должна
его уменьшить за счёт масок SAM2 и триангуляции, но убрать полностью без изменения кадров трекера
нельзя. Если критерий демо — отсутствие шагов > 10 м, а заполнение длинного провала (815–1041)
всё равно расходится, разумный компромисс — заполнять провал только пока есть наблюдения, а
чистый прогноз ограничить по времени.

Каждая оценка проверяется на правдоподобие: внутри зоны камер и не ниже самой низкой камеры
больше чем на 25 м (так на старом трекере отсеялся огонь, принятый за фуру). Всё причинно —
только текущий и прошлые кадры. Скорость на заполненных кадрах не считается (пустое поле).

Также в ветке:
- `tools/no_gt_metrics.py` — метрики без эталона: засечки по 2+ камерам, физика траектории,
  режимы трекера; `docs/way2/checks.json` — 4 ручные засечки центра фуры. Засечки ставят центр
  рамки, а трекер выдаёт точку у кабины, поэтому несколько метров — разница точек, а не ошибка.
- `web/viewer.js` — подписи новых статусов.
- `tests/test_gap_fill.py` — `python -m pytest tests` (21 passed).

## Как проверить

Тот же запуск, что для демо (заполнение включено само):

```bash
python -m online.run --data data/way2 --out out/way2-fill --global-seg models/yolo26l-seg.pt --sam-video facebook/sam2.1-hiera-base-plus --video
```

Для сравнения — без заполнения (должно совпасть с текущим демо):

```bash
python -m online.run --data data/way2 --out out/way2-base --global-seg models/yolo26l-seg.pt --sam-video facebook/sam2.1-hiera-base-plus --no-fill-gaps
```

Что смотреть:
1. Кадры трекера не изменились: все кадры, где у `way2-base` есть координаты, совпадают с `way2-fill`.
2. Провалов нет: в `way2-fill/trajectory.csv` координаты на всех кадрах, кроме тех, где фура ещё
   ни разу не видна.
3. Точность заполненных кадров:
   `python tools/no_gt_metrics.py --out out/way2-fill --data data/way2 --checks docs/way2/checks.json`
   (кадр 1400 — внутри провала 1418–1499 его не задевает, а засечки Коли в `report.json` — точнее).
4. Way1 не должен измениться совсем, если там нет кадров `lost`.

Без ffprobe синхронизация по PTS не запустится — тогда `--sync index` (в Way2 у всех камер не
хватает только последнего кадра, результат тот же).

## v3 (после проверки v2 на Linux: 33 шага > 10 м, 172 м на кадре 1042)

Причина v2: внутри провала поправка по одной камере ставила фуру на «высоту дороги» вдоль луча
камеры 4, а высота была испорчена оценками `mask_multi` (−1,7 м). Ответ уехал по лучу назад на 40 м,
хотя фура ехала вперёд, а прогноз выучил эту ложную скорость и 140 кадров уезжал не туда.

Исправлено:
- одна камера — только поперечная к лучу поправка (ближайшая к прогнозу точка луча), без дальности
  ни по размеру маски, ни по пересечению с дорогой;
- скорость прогноза учится только на триангуляции двумя камерами;
- высота дороги — только по кадрам `multi`;
- слабые детекции YOLO и отброшенные маски трекера — только рядом с проекцией прогноза (IoU ≥ 0,3);
- затухание скорости 1 % за кадр (полжизни ~2,3 с): в слепом провале ответ не уезжает далеко.

Офлайн-проверка без видеокарты на replay опубликованного демо (наблюдения — его `tracked_2d_boxes`,
слабые детекции YOLO не моделируются):

```bash
python tools/sim_gap_fill.py . out/way2-base/replay.json data/way2
```

| | v2 | v3 |
|---|---|---|
| Скачок на возврате, кадр 1042 | 228 м (на Linux 172 м) | **49 м** |
| Наибольший шаг внутри провалов | до 228 м | ≤ 1,5 м (кроме стыков) |
| Шагов > 10 м всего (база — 7) | — | 11 |

Из четырёх лишних шагов три — собственные скачки трекера через провал в 1–5 кадров, которые
заполнение лишь делает видимыми: 777 → 779 трекер прыгает на 14,6 м, 1410 → 1412 — на 12,7 м
(в базе между ними пустой кадр, поэтому шаг не считается). Реально от заполнения — стык 1042:
с 905 по 1041 (4,5 с) фуру не видит ни одна камера, а она в это время поворачивает
(814 → 1042: 58 м). Без будущих кадров этот стык меньше не сделать, не трогая кадры трекера.
